# Lab 02: VHDL ALU Verification with cocotb

## Overview

This lab builds and verifies an **8-bit Arithmetic Logic Unit (ALU)** written in VHDL.

The main goal is to move beyond basic hardware testing and develop a structured verification environment using **cocotb**, **GHDL**, and a **Python reference model**.

The ALU supports eight arithmetic, logical, comparison, and shift operations. Its behavior is verified using directed tests, randomized testing, systematic boundary-value testing, and exhaustive verification across the complete input space.

The lab also includes waveform analysis, intentional RTL fault injection, and automated verification using GitHub Actions.

This lab focuses on:

## ALU Architecture

The ALU accepts two 8-bit operands and a 3-bit operation code.

```text
                    opcode[2:0]
                        │
                        ▼
                 ┌─────────────┐
        A[7:0] ─►│             │
                 │     ALU     ├──► result[7:0]
        B[7:0] ─►│             │
                 └──────┬──────┘
                        │
                        ├──► zero
                        │
                        └──► carry
```

### Inputs

| Signal | Width | Description |
|---|---:|---|
| `a` | 8 bits | First ALU operand |
| `b` | 8 bits | Second ALU operand |
| `opcode` | 3 bits | Selects the ALU operation |

### Outputs

| Signal | Width | Description |
|---|---:|---|
| `result` | 8 bits | ALU operation result |
| `zero` | 1 bit | Set when the result is zero |
| `carry` | 1 bit | Carry-out generated by addition |

---

## Supported Operations

| Opcode | Operation | Description |
|---|---|---|
| `000` | ADD | Addition |
| `001` | SUB | Subtraction |
| `010` | AND | Bitwise AND |
| `011` | OR | Bitwise OR |
| `100` | XOR | Bitwise XOR |
| `101` | SLL | Logical shift left |
| `110` | SRL | Logical shift right |
| `111` | SLT | Unsigned set-less-than comparison |

## Python Reference Model

A Python reference model is used as the expected behavioral model of the ALU.

Instead of hard-coding an expected result for every test, the same operands and opcode are provided to both the VHDL ALU and the Python model.

```text
                    a, b, opcode
                         │
                ┌────────┴────────┐
                ▼                 ▼
            VHDL ALU        Python Model
                │                 │
                ▼                 ▼
          Actual Output     Expected Output
                │                 │
                └────────┬────────┘
                         ▼
                       Compare
                         │
                    PASS / FAIL
```

The model calculates:

- Expected result
- Expected carry flag
- Expected zero flag

This provides a reusable verification method for every supported ALU operation.

## Verification Strategy

The ALU is verified using several complementary testing methods.

### 1. Directed Testing

Known input combinations are used to verify all eight operations and important boundary conditions.

Examples include:

```text
10 + 20
255 + 1
20 - 10
10 - 20
0xAA AND 0x55
0xA0 OR 0x05
0xAA XOR 0xFF
1 << 1
128 >> 1
10 < 20
20 < 10
```

Directed tests make it easy to target important behavior explicitly.

### 2. Randomized Verification

Random values are generated for:

```text
A       = 0 to 255
B       = 0 to 255
opcode  = 0 to 7
```

Each generated input is evaluated by both the VHDL DUT and the Python reference model.

The lab performs **1,000 randomized ALU tests**.

### 3. Systematic Boundary Testing

A selected set of important values is tested against every operation.

The values include:

```text
0
1
2
15
16
127
128
254
255
```

With eight operations and all pairs of these values:

```text
8 × 9 × 9 = 648 checks
```

This provides focused testing around useful numerical boundaries.

### 4. Exhaustive Verification

Because the ALU input space is still manageable, every possible combination is tested.

```text
256 possible A values
×
256 possible B values
×
8 possible opcodes
=
524,288 combinations
```

The Python reference model is used as the expected result for every combination.

This verifies the complete defined input space of the 8-bit ALU.

## Flag Verification

The testbench verifies both ALU status outputs.

### Carry Flag

For addition, the operands are extended before addition so the carry-out bit is preserved.

For example:

```text
255 + 1 = 256

9-bit representation:

1 00000000
│ └──────┘
│     │
│     └── result = 0
│
└──────── carry = 1
```

### Zero Flag

The zero flag is asserted whenever the 8-bit ALU result is zero.

```text
result = 00000000
        ↓
      zero = 1
```

Otherwise:

```text
result != 00000000
        ↓
      zero = 0
```

## Waveform Analysis

A short dedicated test sequence is used for waveform generation instead of running the full exhaustive test.

The waveform contains the following signals:

```text
a
b
opcode
result
carry
zero
```

A GHDL waveform can be generated using:

```bash
make clean
make COCOTB_TESTCASE=test_waveform_demo SIM_ARGS="--wave=alu_wave.ghw"
```

The waveform can then be inspected using GTKWave:

```bash
gtkwave alu_wave.ghw
```

Waveform inspection provides a visual way to confirm how inputs, operation codes, outputs, and flags change during simulation.

## Intentional RTL Fault Injection

Testing correct RTL alone does not demonstrate whether a testbench can detect incorrect hardware.

For this reason, several intentional RTL faults were temporarily introduced.

### Fault 1: ADD Carry Bug

The correct carry logic was deliberately replaced so that the carry output always remained zero.

A case such as:

```text
255 + 1
```

should produce:

```text
result = 0
carry  = 1
```

The faulty implementation instead produced an incorrect carry value, and the verification environment detected the mismatch.

### Fault 2: SLT Comparison Bug

The unsigned less-than comparison:

```vhdl
unsigned(a) < unsigned(b)
```

was intentionally changed to the opposite comparison.

Directed tests successfully detected the incorrect SLT behavior.

### Fault 3: Shift-Left Bug

The logical shift-left implementation was temporarily replaced with a right shift.

The verification environment detected the incorrect result.

After each experiment, the correct RTL was restored and the regression tests were rerun.

The lab is integrated with **GitHub Actions**.

## Key Lessons

This lab demonstrates that hardware verification becomes easier to scale when the expected behavior is separated from the RTL implementation.

The Python reference model acts as an independent behavioral specification. The same verification infrastructure can then be reused for directed, randomized, systematic, and exhaustive testing.

Fault injection also demonstrates an important principle: a verification environment should not only pass correct hardware. It should fail when the hardware is wrong.
